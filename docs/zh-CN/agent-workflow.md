# 仓库工作流程

修改代码前阅读 `CONTRIBUTING.md`、`docs/iteration-plan.md` 和相关组件文档。以当前仓库与 CI 状态为事实依据；历史报告描述各自记录的修订版本。

- 保持 Java 17 为最低运行时和字节码目标，并在 Java 17、21 和 25 上检查兼容性。保持内核不依赖第三方生产库，也不承载应用策略。
- 每次实现一个聚焦且可验证的增量。优先处理已确认失败与回归，再推进就绪计划项。在同一拉取请求中更新计划，附上证据与剩余工作。不要为了填满一次计划运行而编造缺陷或仅做表面修改。
- 对照源码和具体反例，独立检查架构提案。选择接入所需的最小行为 profile；共享数据结构不意味着必须建立统一状态机、媒体时间线或验证套件。纠正缺乏依据的假设，不把另一份评审的认同当作证明。除非内核调度／生命周期确实需要，新领域契约保持可选。
- 保留用户尚未完成的变更。先检查分支、工作树和开放的拉取请求；承接匹配的未完成工作，不重复创建。在同一检出目录串行构建。若本地工作冲突，通过可用工作区工具创建隔离检出。
- 使用 `codex/` 分支。通过拉取请求发布到受保护的 `main`；不得直接推送到 `main`、强制推送、绕过保护，或在必需检查失败／待完成时合并。要求当前 head 的 `verify (17)`、`verify (21)`、`verify (25)`、`source-hygiene` 和 `container` 通过，并解决评审讨论。仅在分支已更新后进行 squash 或 rebase。
- 为变更执行有意义的检查。运行时变更要求 Java 17 覆盖率／SBOM 验证及相关失败／生命周期测试。调度或分配变更还需可比较的性能证据。保留有界工作、取消、generation 隔离、不可变媒体帧与资源释放。
- 记录基准范围、JVM／主机、源码与产物哈希、预热、独立进程数、分配及不确定性。在同一主机／JVM／设置上比较修订。带噪声的共享 CI 运行器是证据采集器，不是性能阈值门禁。不要将内核吞吐换算为模型／网络延迟或生产容量。
- 使用剖析工具生成 CPU、分配和 GC 摘要。只打包诊断白名单。凭据、应用录音、原始 JFR、堆转储和未审查本地日志不得进入公开产物。默认使用合成测试夹具。
- 只有操作者显式配置端点、模型和凭据环境变量名后，才运行外部提供方试验。不得在无关用户文件中搜索密钥。缺少访问权限只阻塞该试验，不阻塞独立本地工作；不得把测试夹具标成真实提供方验证。
- 完成的增量应有可复现证据、准确文档，以及已通过绿色检查并合并的拉取请求。若无法完成运行，保留分支与具体下一步行动。不要仅因一次迭代结束而变更发行资产或打标签发版。
