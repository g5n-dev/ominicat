# 性能深度审计

本次审计检查框架自身的本地工作，不包含模型与网络延迟，并区分源码可确认的工作量与实测优化收益。现有数值帧竞品对比不覆盖提示词构造、媒体编解码、异步提供方或 Studio 观测。

## 已验证的提示词渲染增量

原提示词路径调用 `ConversationWindow.snapshot()` 只为获取轮次，却同时重算了区间并集及逐说话人统计。它先拼出全部保留历史再丢弃旧行，即使模板没有引用历史也会如此。生成相同提示词并不需要这些工作。

优化后读取只含轮次的不可变快照，在构造时缓存历史占位符数量，只构建能放入字符预算的完整历史后缀。模板不使用历史时，检查基础提示长度后直接返回。转写保留、去重、异常消息、中断、UTF-16 预算与单遍替换维持现有行为；公开评估快照仍计算完整指标。

[Linux 配对工作流](../../.github/workflows/prompt-cost.yml)使用同一份 [JMH 探针](../../ominicat-benchmarks/src/main/java/io/ominicat/benchmarks/PromptCostProbe.java)，切换基线与候选运行时 JAR。九种用例覆盖 32、256、10,000 条保留记录，以及不使用历史、完整历史、截短历史。准备阶段在计时外填满窗口；每次测量创建新最终转写、更新真实窗口、渲染并逐字校验预期输出。两版计时均包含完整字符串校验。这是提示词阶段成本，不是内核分发或端到端对话延迟。

同一 Ubuntu 24.04／Java 17 作业依次执行基线 → 候选 → 候选 → 基线：每版每用例有两个独立 JVM，每个 JVM 预热三次一秒、测量五次一秒。每个进程核对实际加载的核心、会话与探针 JAR 哈希。[采集器](../../scripts/prompt_cost.py)拒绝缺失矩阵、原始数据变更、运行时与设置混用。共享运行器仍有噪声；观察范围不是置信区间，也不代表生产容量。

## 历史 Linux 内核基线

[Java 17 profile 作业](https://github.com/g5n-dev/ominicat/actions/runs/41237014639)记录了版本 208b0c4 的内核，环境为 Linux/amd64、Temurin 17.0.21，四个可用处理器。[完整白名单归档](reports/performance-audit/linux-java17-2026-11-01/report.md)绑定源码、产物哈希、JMH 设置及 CPU／分配／GC 图表。三个独立 JVM 各预热五次两秒、测量八次两秒；表中保留 JMH 的 99.9% 误差估计。直接派发和会话往返是两种独立负载。这些历史数值不是对后续直接路径实现的测量。

在该次采集中，每新增一个阶段，直接派发的整体分配约增加 72 B，会话路径约增加 80 B。这包含变换后的数值帧和调用机制，不能单独归因为保护对象的成本。整段记录的分配采样也出现了捕获的续接对象与作用域接收器。这些观测促成了下方直接路径实验；它们不是当前的每次操作分配量，也不是加速保证。归档报告中关于开发机器共享的通用句子属于模板提示；真实采集环境以所链 GitHub 运行器为准，其其他租户并未被观测。

该 CPU 记录共有 1,200 个叶节点样本，其中 637 个位于 LockSupport.unpark。其完整提供栈中，150 个经过会话有效性检查，302 个经过负载驱动的信号量释放，77 个经过取队列操作。不能把全部 unpark 样本都归因于内核有效性检查，否则会错误归因测量程序的成本。样本包含预热／负载／排序阶段，不是耗时百分比。

## 已验证的直接调用状态

[直接调用状态报告](reports/performance-audit/direct-state-2026-11-02/README.md)记录了[Ubuntu 作业 41401882524](https://github.com/g5n-dev/ominicat/actions/runs/41401882524)中候选 f5454f4 与基线 c2def9d 的比较。生产内核源码只有 `Pipeline.java` 改变：每条流水线预先绑定不可变的处理器／后继拓扑，每次直接阶段调用仍创建包含 `owner`、`nextStage` 和 `output` 的新状态，并在 `finally` 中断开引用。两版均运行相同生命周期回归，保留线程／寿命拒绝、空值处理、过滤／多次输出、嵌套调用、异常传播和引用释放。

同一份探针 JAR 分别搭配置于类路径首位的两份实际内核 JAR，核对加载来源及源码／产物哈希。七种场景执行三个 ABBA 配对块，其中中间配对块反转场景顺序：在同一 Ubuntu 24.04 主机上运行 84 个全新 Java 17 JVM，每侧、每种场景有六个 fork，每个 fork 预热三轮各 1 秒、测量五轮各 1 秒。主场景 raw-direct-4 的分配约从 **352 降至 256 B/op**，下降 **27.27%**，**配对块平均耗时下降 20.09%**。Envelope-direct-4 记录的**分配下降 8.39%**、**耗时下降 3.57%**。[指标阅读指南](performance.md#如何阅读这些指标)解释单位、归一化、配对块比值和不确定性。

[![配对直接调用状态耗时与分配](../assets/previews/reports--performance-audit--direct-state-2026-11-02--costs-zh-CN.png)](../assets/zh-CN/reports/performance-audit/direct-state-2026-11-02/costs.svg)

全部六个直接调用场景在每个配对块都满足原定规则：主场景分配比 ≤0.90、直接调用耗时比 ≤1.05、分配比 ≤1.01。点估计取三个配对块比值的算术平均值；范围是观测范围而非置信区间，迭代也不是独立 fork。源码变更、生命周期检查和配对的实际 JAR 测量支持这项组合直接路径变更的效果，不证明物理对象数量、某个独立 JIT 机制，也不能解释此前 Camel 差距。未改变的会话对照如实报告，不用于噪声校正，也不宣称会话加速。首轮 `targets-not-met` 与第二轮 `uncertain` 归档保持完整，不合并不同托管作业的数据。

这项优化有构建成本取舍。独立的八 JVM 诊断观测到：新建四阶段流水线的分配约**增加 136 B/op**；新建后再执行首次直接调用，分配约**增加 32 B/op**。两者都使用已预热 JVM，不是操作系统/JVM 冷启动；仅用于同步会话的流水线也会承担预绑定计划的成本。两个 fork 的范围仍然可查，不改变主实验验收。不得将构建与稳态探针相减，以推导精确摊销点或容量。主实验的媒体场景使用预先构造的不可变帧，不测快照构造或编解码。已验证的切片是同步直接派发；更广泛的会话／异步分配和媒体构造仍需独立工作。

## 其余优化候选

| 候选 | 已确认的工作 | 改变行为前需要的证据 |
| --- | --- | --- |
| 会话／异步调用分配 | [会话派发](../../ominicat-core/src/main/java/io/ominicat/core/Pipeline.java)仍使用捕获的续接对象和作用域接收器。上方仅针对直接调用的表示变更没有改变该路径；单凭采样不能得到每操作分配量。 | 匹配的普通帧／信封外部回调探针，保留有界工作、取消、代次栅栏和引用释放，并采集配对耗时／分配证据。不能将直接调用结果扩展到这些路径；媒体构造也需要独立探针。 |
| 代次有效性读取 | [会话有效性检查](../../ominicat-core/src/main/java/io/ominicat/core/PipelineSession.java)在每个阶段边界及最终输出获取会话锁。 | 多提交者竞争、有界在途负载及配对 CPU／延迟／分配证据。正确发布的逐代票据只是实验方案，不能用普通无同步字段读取替代取消栅栏。 |
| 出站线协议中间表示 | [帧编码](../../ominicat-server/src/main/java/io/ominicat/server/FrameCodec.java)创建 JSON 树、Base64 与字符串，随后[传输层](../../ominicat-server/src/main/java/io/ominicat/server/OminiCatServer.java)计算 UTF-8 字节并创建网络帧。 | 先隔离文本／音频／图像编码，再试内部字节输出路径。保留公开编码、Unicode、精确字节上限、顺序和缓冲释放；保留不可变输入快照。 |
| 活动记录锁范围 | [日志读取](../../ominicat-server/src/main/java/io/ominicat/server/ActivityJournal.java)持有与被追踪写入者相同的监视器，完成整页事件序列化。 | 多会话追加与并发分页，精确游标／缺口检查，以及有界不可变事件快照。开启观测的负载应与默认会话分开测量。 |
| 转写请求复制 | [转写缓冲](../../ominicat-providers/src/main/java/io/ominicat/providers/TranscriptionFactory.java)使 PCM 经过临时块、累积缓冲、WAV 与 multipart 实体化。源码至少可确认上传前六次载荷长度的复制，不含扩容、不可变输入构造和 HTTP 内部。这是复制次数，不是实测分配或 RSS。 | 分开测追加、WAV 及完整请求构造，逐字节验证输出，并检查流隔离、中断及接近上限的输入。保留防御性所有权。 |
| SSE 解析 | [聊天解析](../../ominicat-providers/src/main/java/io/ominicat/providers/ChatFactory.java)对流式文本逐字符扫描、组装行／事件，并解析 JSON 树。 | 用内存 UTF-8 事件及碎片化读取测每事件分配和首事件交付。保留严格解码、限制、取消、CR 处理和显式完成标记。 |
| 并行结果复制与刷出合并 | [分支汇合](../../ominicat-core/src/main/java/io/ominicat/core/ParallelProcessor.java)复制私有引用缓冲；传输逐输出刷出。 | 二者分别测量。转移引用可能更久保留富余容量，合并刷出可能恶化单帧尾延迟。保留全成功后的有序汇合、截止时间和逐帧传输预算预留。 |

## 验收与后续

提示词回归测试使用独立构造的后缀预期逐字比较完整输出，覆盖随机事件序列、重复占位符、Unicode、字面占位符文本、错误、去重与中断。仍要求常规 Java 17／21／25 检查通过；运行时变更需要覆盖率／SBOM 验证和 512 个压力种子。

同步直接派发现已成为已验证的切片。其余会话／异步和媒体构造实验仍遵循[现有基线要求](iteration-plan.md#性能证据)。异步弱引用、代次栅栏、作用域接收器与不可变媒体快照承担已经验证的生命周期职责。源码检查用于提出候选；其他路径的收益仍需匹配的前后证据。
