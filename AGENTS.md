# Repository workflow

Read `CONTRIBUTING.md`, `docs/iteration-plan.md` and the relevant component documentation before changing code. Use the current repository and CI state as the source of truth; historical reports describe their recorded revisions.

- Keep Java 17 as the minimum runtime and bytecode target, with compatibility checks on Java 17, 21 and 25. Keep the kernel free of production dependencies and application policy.
- Implement one focused, verifiable increment at a time. Prioritize confirmed failures and regressions over the next ready plan item. Update the plan in the same pull request with evidence and remaining work. Do not invent defects or make cosmetic changes just to fill a scheduled run.
- Preserve unfinished user changes. Check the branch, working tree and open pull requests first; resume matching work instead of creating a duplicate. Run builds serially in a checkout. If local work conflicts, use an isolated checkout through the available workspace tools.
- Work on a `codex/` branch. Publish through a pull request to protected `main`; never push directly to `main`, force push, bypass protection or merge a failing/pending required check. Require `verify (17)`, `verify (21)`, `verify (25)`, `source-hygiene` and `container` at the current head, and resolve review conversations. Squash or rebase only after the branch is current.
- Run meaningful checks for the change. Runtime changes require the Java 17 coverage/SBOM verification and relevant failure/lifecycle tests. Scheduling or allocation changes also need comparable performance evidence. Preserve bounded work, cancellation, generation fences, immutable media frames and resource release.
- Record benchmark scope, JVM/host, source and artifact hashes, warmup, forks, allocation and uncertainty. Compare revisions on the same host/JVM/settings. A noisy hosted runner is an evidence collector, not a performance threshold gate. Do not translate kernel throughput into model/network latency or production capacity.
- Generate CPU, allocation and GC summaries with the profiling tools. Package only the diagnostic allowlist. Keep credentials, application recordings, raw JFR, heap dumps and unreviewed local logs out of published artifacts. Use synthetic fixtures by default.
- Run external provider trials only with an explicitly configured endpoint, model and credential environment-variable name. Never search unrelated user files for secrets. Missing access blocks that trial, not independent local work; do not label fixtures as live-provider validation.
- A completed increment has reproducible evidence, accurate documentation and a merged green pull request. If a run cannot finish, preserve its branch and concrete next action. Do not change release assets or tag a release merely because an iteration finished.
